Week 1 · Evaluation foundationsThe harness the whole team depends on.
W1Build a reusable eval harnessA drop-in runner: golden set + LLM-judge + Ragas.▸
Steps
  1. Define a dataset format (input, output, contexts, ground_truth).
  2. Add a golden-set runner and an LLM-as-judge scorer.
  3. Wire Ragas for RAG metrics and return one summary.
Tools
ragas datasets anthropic SDK
Starter code
# uv add ragas datasets
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy

def run_eval(app_fn, dataset):
    rows = []
    for ex in dataset:
        out = app_fn(ex["input"])
        rows.append({"question": ex["input"], "answer": out["answer"],
                     "contexts": out["contexts"], "ground_truth": ex["truth"]})
    return evaluate(to_hf(rows), metrics=[faithfulness, answer_relevancy])

# expose run_eval so D1-D4 can `from harness import run_eval`
✓ Done when: Any teammate can import your harness, pass their app + dataset, and get scores back.
⚠ Watch out: Make it framework-agnostic — it should score a plain function, so every domain can use it without adopting your internals.
W1Add an LLM-as-judge with a rubricScore open-ended answers consistently.▸
Steps
  1. Write a rubric (what 1–5 means).
  2. Have a judge model score answers against it.
  3. Mitigate bias (randomize order in pairwise, pin the judge model).
Tools
anthropic SDK
Starter code
def judge(question, answer, rubric):
    m = a.messages.create(model="claude-sonnet-4-5", max_tokens=200,
        messages=[{"role":"user","content":
            f"Rubric:\n{rubric}\n\nQ: {question}\nA: {answer}\n"
            "Return JSON: {\"score\":1-5,\"reason\":\"...\"}"}])
    return json.loads(m.content[0].text)
✓ Done when: The judge returns a consistent score + reason against your rubric on a sample set.
⚠ Watch out: Judges have biases (length, position, self-preference). Pin the judge model and spot-check it against human labels.
Week 2 · Agentic eval & routing policyEvaluating agents and proving routing pays off.
W2Add trajectory / tool-call evalScore how the agent worked, not just the answer.▸
Steps
  1. Capture the agent’s trace (steps + tool calls).
  2. Check tool-call correctness and step validity.
  3. Add task-success scoring on top.
Tools
your harness D3 traces
Starter code
def eval_trajectory(trace, expected_tools):
    used = [s["tool"] for s in trace if s.get("tool")]
    tool_ok = set(expected_tools) <= set(used)
    no_loops = len(used) == len(set(used)) or len(used) < 12
    success = trace[-1].get("status") == "done"
    return {"tool_ok": tool_ok, "no_loops": no_loops, "success": success}
✓ Done when: The harness reports tool-call correctness and task success for D3’s agent.
⚠ Watch out: An agent can get the right answer the wrong way (unsafe write, 30 wasted steps). Trajectory eval catches what answer-only eval misses.
W2Define a routing policy + cost/quality comparisonProve cheap-vs-frontier routing saves money safely.▸
Steps
  1. Define cost/quality tiers and a fallback chain.
  2. Run the same eval set across tiers.
  3. Show the cost saved and the quality delta.
Tools
litellm your harness
Starter code
tiers = {"cheap":"openai/gpt-4o-mini", "frontier":"anthropic/claude-sonnet-4-5"}
report = {}
for name, model in tiers.items():
    score = run_eval(lambda x: ask(x, model=model), golden)
    report[name] = {"quality": score, "cost": total_cost()}
print(report)   # the table you show a customer
✓ Done when: You can show a table: routing cuts cost by X% with an acceptable quality delta.
⚠ Watch out: Routing that saves money but quietly drops quality is a net loss. The policy must include a quality floor, not just a budget.
W2Document the model-adaptation callKnow when to recommend fine-tuning vs prompt/RAG.▸
Steps
  1. Write the decision: prompt → RAG → routing → fine-tune.
  2. Note what fine-tuning costs (data, time, maintenance).
  3. Capture the signal that justifies it (a narrow task still failing).
Tools
your eval data
Starter code
Decision note template:
  problem: <narrow, repeated task> still fails after prompt+RAG+routing
  evidence: eval score stuck at X over N attempts
  options: LoRA (self-host) vs managed FT; data needed: ~K examples

Week 3 · GuardrailsStopping the bad stuff at the edges.
W3Build ingress/egress guardrailsValidate I/O, block injection, verify citations.▸
Steps
  1. On input: validate schema and screen for injection.
  2. On output: enforce format and check claims are cited.
  3. Reject or repair anything that fails.
Tools
pydantic your harness
Starter code
def ingress(text):
    assert len(text) < 8000, "input too long"
    if any(p in text.lower() for p in ("ignore previous","system prompt")):
        flag("possible injection", text)
    return text

def egress(answer, contexts):
    # every factual sentence should map to a provided context
    if not citations_supported(answer, contexts):
        return "I can only answer from the provided sources."
    return answer
✓ Done when: Injection attempts are flagged on input and uncited claims are blocked/repaired on output.
⚠ Watch out: Guardrails are defense-in-depth, not a single filter. One regex won’t stop injection — layer input checks, output checks, and least privilege.
Week 4 · Security, governance & complianceWhat enterprise buyers actually ask about.
W4Add PII redaction + an audit logMinimize data exposure and record every action.▸
Steps
  1. Detect and redact PII before it hits the model/logs.
  2. Append an immutable audit record per request/action.
  3. Document a tenant-isolation approach.
Tools
presidio an append-only store
Starter code
# uv add presidio-analyzer presidio-anonymizer
from presidio_analyzer import AnalyzerEngine
from presidio_anonymizer import AnonymizerEngine
an, anon = AnalyzerEngine(), AnonymizerEngine()

def redact(text):
    found = an.analyze(text=text, language="en")
    return anon.anonymize(text=text, analyzer_results=found).text

audit_append({"ts": now(), "tenant": tid, "action": "invoke", "pii_redacted": True})
✓ Done when: PII is redacted before model/logs, and each request leaves an immutable audit entry.
⚠ Watch out: Redact before logging, not after — a log line with raw PII is itself the breach. And keep audit logs append-only.
Week 5 · DeploymentFrom ‘runs on my machine’ to ‘runs for a customer’.
W5Containerize + CI that runs eval & smoke testsEvery change is built and gated automatically.▸
Steps
  1. Write a Dockerfile for the service.
  2. Add a CI workflow that builds, runs smoke tests, and runs the eval.
  3. Block merges on failure.
Tools
docker github actions
Starter code
# .github/workflows/ci.yml
name: ci
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t app .
      - run: docker run app pytest -q          # smoke tests
      - run: docker run app python eval.py --min-score 0.8   # eval gate
✓ Done when: Opening a PR builds the image, runs smoke tests + eval, and fails the check on regression.
⚠ Watch out: Pin versions and bake secrets in at runtime (env), never in the image. A baked-in key ships to everyone with the image.
Week 6 · Observability & costYou can’t operate what you can’t see.

Steps
  1. Instrument calls with tracing (LangSmith/Langfuse or OTel).
  2. Record tokens, cost, latency, and eval scores per span.
  3. Surface them on a dashboard.
Tools
langfuse / langsmith opentelemetry
Starter code

from langfuse.decorators import observe
@observe()
def invoke(question):
    # spans auto-captured; attach metrics
    log_metric("tokens", n); log_metric("cost_usd", c); log_metric("latency_ms", ms)
    return answer
✓ Done when: A request produces a trace with per-step tokens, cost, and latency visible on a dashboard.
⚠ Watch out: Trace sampling vs full capture is a cost choice — capture everything in dev, sample in high-volume prod.
W6Add a semantic cache; measure hit-rateCut cost/latency on semantically repeated queries.▸
Steps
  1. Embed incoming queries; on a near-duplicate hit, return the cached answer.
  2. Track hit-rate and the cost/latency saved.
  3. Set a similarity threshold that avoids wrong hits.
Tools
embeddings a vector cache
Starter code
def cached_answer(q, threshold=0.95):
    qv = embed(q)
    hit = cache.nearest(qv)
    if hit and hit.score >= threshold:
        metrics.incr("cache_hit"); return hit.answer
    ans = run_llm(q); cache.put(qv, ans); return ans
✓ Done when: Repeated/near-duplicate queries hit the cache, and you can show the hit-rate and savings.
⚠ Watch out: Too low a threshold returns a confidently wrong cached answer. Tune it and exclude personalized/time-sensitive queries.

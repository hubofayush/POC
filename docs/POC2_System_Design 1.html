System Architecture — how the five domains fit together

D1 RAG (policies & regs) D2 Memory D3 Agents (LangGraph) D4 MCP & Connectors D5 HIPAA & Security (wraps all)

Read it top-down: a document upload or question enters through D5 ingress (auth + RBAC + PHI redaction) → the D3 orchestrator runs the Document, Verification, Compliance and Report agents, reading D2 history and calling D1 (policies) and/or D4 (credential/government APIs, OCR, HRMS) over /invoke → it composes a cited, verified result → D5 masks PHI, validates & logs on egress → D2 stores the verification. Every box is a standalone product; the arrows are just /invoke and tool calls.

The four agents — how D3 decomposes verification

Document AgentIngests the upload, runs OCR + face/signature checks, extracts structured fields (name, license #, issue/expiry dates) and classifies the document type.
Verification AgentCross-checks extracted fields against D1 policies and D4 authoritative sources (credential + government APIs); flags mismatches, expiry and forgery signals.
Compliance AgentEvaluates a clinician/org against the required credential set and regulations (HIPAA, licensure) — surfaces gaps, expiries and non-conformance.
Report AgentComposes the compliance report / AI summary / credential timeline with citations, and routes notifications to HR via Email/HRMS.

Example Flows — how the sample questions travel through the system

UUser D5Security/Obs D3Agents D2Memory D1RAG D4Connectors HHuman

0 · Upload & verify a credential (core pipeline)

A clinician uploads a nursing license.
  • UClinician/HR uploads a license document.
  • D5Ingress: auth + RBAC + PHI redaction + consent.
  • D4OCR extracts fields; face + signature checks run.
  • D1Embed + RAG the matching licensure policy.
  • D3Verification Agent cross-checks fields vs policy.
  • D4Government API confirms the license is genuine & active.
  • D3Report Agent writes the compliance record.
  • D4Notify HR via Email/HRMS; D5 logs the action.

1 · Expiry check (verification read)

“Is this nursing license expired?”
  • UUser asks about a specific license.
  • D5Ingress validation + RBAC (may they view it?).
  • D2Recalls the clinician & prior verifications.
  • D3Verification Agent reads the stored expiry date.
  • D4Optionally re-checks the government registry for currency.
  • D5Egress: answer cited to the record/source; logged.
  • U“Expired on 12 Mar — renewal required.”

2 · Source comparison (verify vs authority)

“Compare uploaded certificate with government records.”
  • UUser requests a source-of-truth comparison.
  • D5Ingress validation + PHI handling.
  • D3Document Agent loads OCR'd fields from the upload.
  • D4Government API returns the authoritative record.
  • D3Verification Agent diffs fields; flags mismatches.
  • D5Egress: every match/mismatch cited to its source; logged.
  • U“Name & number match; issue date differs — flagged.”

3 · Missing credentials (compliance gap)

“Show missing credentials for Dr. John.”
  • UHR asks for a clinician's gaps.
  • D5Ingress validation + RBAC (HR scope).
  • D2Loads Dr. John's org, role & verification history.
  • D1Retrieves the required credential set for the role.
  • D3Compliance Agent diffs required vs held → gaps + expiries.
  • D5Egress: PHI-safe list, cited to policy; logged.
  • U“Missing: BLS cert; HIPAA training expired.”

4 · Compliance report (multi-source + notify)

“Generate compliance report.”
  • UCompliance officer requests an org report.
  • D5Ingress flags a downstream notify action.
  • D2Loads org roster & latest verification states.
  • D1Retrieves the applicable regulations.
  • D3Compliance + Report Agents assemble status per clinician.
  • HHuman-in-the-loop: officer reviews before sending.
  • D4On approval, HRMS/Email delivers the report.
  • D5Egress + immutable audit log of the report.

5 · Adaptation decision (design-time)

Internal: “Why is a verification wrong / too slow / too expensive?”
  • D5Eval flags a faithfulness, cost or latency problem.
  • D3Try better prompt + OCR/retrieval first (cheapest fix).
  • D1If it's a policy gap → fix chunking / add regulations / re-index.
  • D3If it's a routing issue → tier the model (cheap ↔ vision/frontier).
  • D5Only if a narrow, repeated extraction stays wrong → fine-tune.
  • D5Prove the change on the golden set before shipping.

Adaptation spectrum: prompt → RAG/OCR → routing → fine-tune. Climb only when the cheaper rung is exhausted.

Platform features — the doc-AI layer (from the SRS)

OCRExtract text & fields from scanned licenses, certs and vaccination records — owned by the Document Agent (D3) over a D4 OCR tool.
Face verificationMatch the photo on the credential to the clinician's identity record; a vision-model check with a confidence threshold.
Signature detectionDetect and validate signatures/seals on documents; flag missing or suspicious marks for human review.
Expiry alertsScheduled scan of stored credentials; D4 Email/HRMS notifies HR ahead of expiry. Backed by D2 history.
AI summaryReport Agent (D3) produces a plain-language, cited summary of a clinician's or org's compliance status.
Credential timelineChronological view of uploads, verifications, renewals and alerts per clinician — assembled from D2 memory.

Two cross-cutting concerns — and who owns them

HIPAA · PHI/PII masking · RBAC

Users only ever see what their role and org allow — and PHI never leaks into logs or answers.
  • D5Owns policy. Auth at ingress, PHI redaction in/out, immutable audit log, tenant isolation, monitoring.
  • D1Permission-aware retrieval — org/role ACLs so restricted docs never enter context.
  • D4Connectors run with least-privilege scopes; government/HRMS calls are minimal-disclosure.

Model routing (which LLM per task)

Cheap model for simple lookups; a vision/frontier model for OCR, face & signature checks.
  • D3Makes the call at runtime — routing is just another orchestration decision.
  • D5Owns the policy — cost/quality tiers, fallback chains, proving it saves money without hurting accuracy.
  • StackOpenAI + Claude behind one interface; hallucination eval scores each variant in LangSmith.

Productionization reality — from mock records to live at a customer

The POC builds on synthetic clinician records and sandbox APIs so no one is blocked. But "swap mocks for real" is the hardest mile — this ladder is what turns the demo into a compliant deployment.

1 · Mock demoEnd-to-end on synthetic records + sandbox government/HRMS APIs. The POC deliverable.
2 · Real data + authOne real connector (e.g. a government registry), real OAuth/secrets, real schema quirks & rate limits.
3 · Security reviewHIPAA controls, RBAC, tenant isolation, PHI masking, least-privilege scopes, audit log, data residency.
4 · Scale & costConcurrency, streaming, p95 latency, Redis caching, model tiering, a cost-per-verification budget that holds.
5 · HandoffRunbooks, LangSmith dashboards, training the customer's compliance team. It survives after you leave.

Why this composes cleanly

Each domain is a black box behind one /invoke endpoint (plus a /stream variant for token/step streaming): send {input, context}, get back {output, citations, metadata}. The D3 orchestrator is the only component that knows the others exist, and it reaches them the way it reaches any tool. So each of the five products is built, tested and demoed alone on mock clinician data — and the same five, unchanged, snap together into the Compliance Platform. Going to a real customer is a config change plus the productionization ladder above: point D1 at their regulations, swap D4's mock credential/government/HRMS connectors for real tenants. No domain has to be rewritten.
